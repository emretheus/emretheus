Jev RAG Benchmark

Does a System One model actually improve a RAG pipeline? I built a free, English benchmark to find out — and kept the runs where the answer was no. This is the study of its decisions, not a feature tour.

evaluation · retrieval · LLM systems Repository ↗ Preregistered protocol ↗ Live leaderboard ↗ Raw artifacts (HF) ↗

The question

TypeSafe's Jev 1.13 returns typed decisions with calibrated probabilities instead of text — a natural fit for one of RAG's quietest jobs: deciding which retrieved passages deserve to reach the model. The same job is done by a free open-weights lookalike, OpenJev, and by a classic cross-encoder. So the benchmark puts all of them on identical frozen candidates and asks a single question: does the model actually improve the system?

The constraints

  • 01

    English data only: XQuAD-EN and SciFact — no translation confound.

  • 02

    $0 budget. Free tiers or the benchmark does not get re-run.

  • 03

    Framework-neutral. The numbers must describe models, not wrappers.

  • 04

    Negative results stay in. Exploratory analyses say so.

The decisions

  1. D1

    A free stack, or a more reproducible one?

    Context
    A benchmark nobody can afford to re-run is a blog post. Reranking evaluations burn tokens on every method you compare.
    Options
    Paid APIs on OpenRouter · local models on a laptop · free tiers of hosted models
    Chosen
    Free tiers only: Codiv for the open model, NVIDIA NIM for embeddings and the cross-encoder, the Vercel AI Gateway free tier for the real Jev.
    Why
    Every published number can be reproduced by anyone with an account, no budget approval. The whole benchmark cost $0 across 1,490 queries and four methods.
    The cost
    Model churn. Three NVIDIA models were retired mid-project and had to be replaced; each swap is recorded in the run manifest so results stay attributable.
  2. D2

    A RAG framework, or a harness of my own?

    Context
    Reranking comparisons are easy to run in LlamaIndex or LangChain — and easy to contaminate with their prompt wrappers, parsers and batching.
    Options
    Adopt a framework · build a thin harness · fork an existing benchmark
    Chosen
    A framework-neutral harness with three runtime dependencies (httpx, numpy, PyYAML).
    Why
    A benchmark should measure models, not wrappers. Fewer layers also means clean latency numbers — and latency is a headline claim for System One models.
    The cost
    The glue has to be written and tested: BM25, reciprocal rank fusion, metrics, calibration, export. That work is the repo.
  3. D3

    How to keep the comparison honest

    Context
    If retrieval re-runs between methods, a lucky or unlucky draw gets published as a model difference.
    Options
    Live retrieval per method · frozen candidate pools · frozen pools plus frozen contexts
    Chosen
    Freeze the top-20 candidates once, compare every reranker on that pool, then replay generation over one frozen top-5.
    Why
    Retrieval, reranking and generation effects are separated by construction. Paired bootstrap confidence intervals compare methods on identical queries.
    The cost
    The stages cannot adapt to each other. A real system could rerank the pool differently per query; the benchmark deliberately cannot.
  4. D4

    Publish the negative result

    Context
    The first run tested the free open-weights OpenJev model. As an always-on reranker it was flat on XQuAD and cost 7.75 nDCG points on SciFact.
    Options
    Quietly swap in a better model · publish the failure · publish the failure and keep testing
    Chosen
    Publish it, then keep testing — with a preregistered protocol and every later analysis labelled exploratory.
    Why
    A benchmark's credibility comes from the runs where its hypothesis loses. The negative result is also the finding: the approach was sound, the free model was not.
    The cost
    The headline is less shiny, and later additions had to carry an honest 'exploratory' label instead of being framed as confirmatory.
  5. D5

    Always-on reranking, or confidence-gated decisions?

    Context
    Ranking every candidate by independent probabilities is noisy. The model's own calibration offered a different interface.
    Options
    Always-on reranking · all-or-nothing switching · confidence-partitioned decisions
    Chosen
    Keep candidates with p ≥ 0.5 in the model's order, fall back to the hybrid order for the rest; skip generation entirely when the top probability is low.
    Why
    The decision layer improved nDCG over the unranked baseline (+0.66 pts on XQuAD, CI excludes zero) and cut generation calls by 31% while raising answer F1.
    The cost
    A threshold must be chosen, documented and re-validated per domain. Gating is a policy, not a property of the model.

The result

nDCG@10 on identical frozen top-20 candidates. Branches: A = no reranker (hybrid order), J = OpenJev 0.1 (free, open weights), N = NVIDIA cross-encoder, T = TypeSafe Jev 1.13.

Dataset n A · no reranker J · OpenJev N · NVIDIA T · Jev 1.13
xquad-en 1190 98.11% 98.03% 99.37% 98.93%
scifact 300 71.67% 63.92% 78.70% 79.29%
  • Jev helps, measurably. +0.82 nDCG points over the unranked baseline on XQuAD (95% CI +0.35 to +1.31) and +7.62 on SciFact (CI +4.88 to +10.38).
  • The free lookalike is not a substitute. OpenJev loses 15.4 points to real Jev on SciFact and actually harms ranking (−7.75 vs baseline). The approach was sound; the free model was not.
  • Against a trained cross-encoder, a tie on SciFact. +0.59 points, CI −1.25 to +2.42 — no measurable difference — while NVIDIA leads XQuAD by 0.45 points.
  • Calibration is the sleeper feature. OpenJev's candidate-level probabilities are well calibrated on XQuAD (ECE 2.5%): at p ≥ 0.5, precision is 94.9% against a 5% base rate. Confidence-gated reranking added +0.66 points over baseline, and answerability gating removed 31% of generation calls while improving answer F1 (31.9% → 33.0%).
  • Every number above cost $0. Codiv's free tier, the NVIDIA NIM trial, and the Vercel AI Gateway free tier.

What failed

  • Assuming the model helps everywhere. On XQuAD the baseline was already at 98.1% nDCG; there was almost nothing left to win, and always-on reranking added noise instead of value.
  • Treating the free clone as a stand-in. On SciFact, OpenJev's always-on reranking lost 7.75 points — a real, statistically clear regression.
  • Ignoring provider lifecycle. Three NVIDIA models were retired mid-run; the pipeline now pins versions and records every resolved model.
  • Expecting free-tier throughput. The gateway answered bursts with 429 and Retry-After: 60; the run settled at roughly one request per second and checkpointed every 100 rows.

What I learned

  • A benchmark's most valuable output is often the constraint map: where the model helps, where it does not, and what it must never be used for.
  • For decision models, calibration is the product. Probabilities are what let a pipeline save money — ranking is just one consumer of them.
  • Report latency with its conditions. The real Jev's 4-second median in the run is an artifact of free-tier pacing; a single request answered in 0.6 seconds. Publishing one number without the other would be misinformation.
  • "No measurable difference" is a real finding. A trust-worthy benchmark needs a home for it.
